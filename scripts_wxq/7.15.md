本地数据包括：
- flights.json：2481 个对话
- hotels.json：2357 个对话
- 合计 4838 个对话
- 每个对话平均约 25–27 个 utterance
- 带细粒度 slot annotation
（1）例如航班中有：
- flight_search.stops
- flight_search.airline
- flight_search.seat_location
- flight_search.time_of_day
- flight_search.price_range
- flight_search.seating_class
（2）酒店中有：
- hotel_search.amenity
- hotel_search.star_rating
- hotel_search.customer_rating
- hotel_search.sub_location.hotel
- hotel_search.type.bed
- hotel_search.price_range
  结论是：
  > 有必要推倒当前 travel v0.3 的模板生成逻辑，基于 Taskmaster 原始对话重新做 grounded、端到端的长程数据。
  
但 Taskmaster 的“ground truth”要正确理解
  Taskmaster 有真实的人类对话和可靠的 slot annotation，但它不是现成的多用户长程 memory 数据：
- 每个 conversation_id 是独立任务
- 没有可复用的长期 user_id
- instruction_id 是任务场景，不是用户身份
- 大多数偏好是“这次请求的约束”，不一定是长期习惯
  例如：
  I want a nonstop flight.
  I'd like an aisle seat.
  I need a hotel with a balcony.
  这些是可靠的当前偏好证据，但不能直接声称这个用户一直偏好 nonstop，真实带有 always/usually/normally 等习惯性措辞的对话很少：
  
- flights：约 12 条
- hotels：约 6 条
  
  因此最终数据应称为：
  
  > Taskmaster-grounded synthetic longitudinal habit benchmark
  
  而不是“真实用户天然形成的纵向 history”。
  

新的正确生成流程
1. 从 Taskmaster 提取 Grounded Preference Evidence

  先把 4838 个对话转换成规范化 source records：

  {
    "source_dataset": "google-research-datasets/Taskmaster-2",
    "source_domain": "flights",
    "conversation_id": "...",
    "instruction_id": "flight-12",
    "user_turns": [...],
    "slot_constraints": {
      "stops": "nonstop",
      "seat_location": "aisle",
      "time_of_day": "evening"
    },
    "explicit_preference_turn_ids": [10, 11]
  }

  这一阶段完全不生成长程数据，只提取真实证据。

2. LLM 从多个真实对话中提炼 Habit

  不能从一条对话直接制造 habit。应该把多条具有一致选择的真实对话组合起来，例如：

  source A：偏好 nonstop，但价格差太大时可接受 layover
  source B：商务行程要求 nonstop
  source C：时间敏感时拒绝 tight connection
  LLM 提炼为：

  {
    "condition": "time-sensitive or business flights",
    "default_action": "prefer nonstop or low-transfer itineraries",
    "boundary": "flexible leisure trips",
    "exception": "a large price difference",
    "source_conversation_ids": ["A", "B", "C"],
    "confidence": 0.91
  }
  每个 habit 必须保留真实来源，不能脱离 source evidence。
3. 将 Habit 聚类为 10–20 个旅行 Habit Family

  Taskmaster flights/hotels 足以支持一组比较自然的 habit：
 （1） 航班方面：
- nonstop vs connection
- price vs reliability
- morning/evening departure
- seat preference
- cabin preference
- airline preference
- connection tolerance
- arrival-time buffer
- trip-type-dependent booking
- flexible vs fixed schedule
  （2）酒店方面：
- location vs price
- star/rating threshold
- breakfast/parking/Wi-Fi
- room/bed type
- quiet vs lively property
- work-trip location preference
- family-room requirements
- accessibility/amenity priorities
- balcony/view preference
- refundable/flexible preference
  全局可以控制在约 12–16 个 family，但每个用户的具体条件和 tradeoff 应来自不同真实 source，不再是复制同一份模板。
4. 生成 Grounded User Dossier

  为每个 synthetic user 组合若干兼容 habit：

  {
    "user_id": "...",
    "travel_profile": {
      "trip_mix": ["business", "family", "short leisure"],
      "budget_sensitivity": "medium",
      "planning_style": "risk-aware"
    },
    "habits": [...],
    "source_conversation_ids": [...]
  }

  habit 数量由画像自然决定，可以是 1–5 个，不追求固定均衡。

5. 让 LLM 先生成完整的长期事件 Arc
  不是先排 support/boundary/exception label，而是先规划用户半年到一年的真实旅行事件：
  1月：临时商务航班
  2月：家庭酒店预订
  3月：普通航班查询
  4月：同类商务行程再次出现
  6月：价格特别高，产生一次例外
  8月：休闲旅行，不适用商务偏好
  10月：新的时间敏感行程
  每个事件引用一个或多个 Taskmaster source record 作为事实和语言 grounding。
6. 按事件 Arc 分块生成完整对话
  每次生成 8–12 个 session，而不是逐条改写模板。
  模型输入包括：
- user dossier
- grounded habits
- source dialogue excerpts
- chronological arc
- 已生成历史摘要
- 当前时间段事件
- 前面出现过的选择和变化
  这样 session 是从用户和事件自然长出来的，不需要 pad_travel_dialogue。
7. 独立重新提炼 Habit
  生成完长程 history 后，换一个独立 pass：
  只给生成后的用户历史
  → 重新提炼 habit
  → 与预设 grounded habit graph 比较

  只有同时满足以下条件才保留：

- habit 能从对话中推断
- source evidence 能回溯到 Taskmaster
- 没有凭空新增 habit
- boundary 和 exception 区分清楚
- 不是通过模板句直接泄露
- 不同 session 的语言和场景足够多样
8. 最后生成 Held-out Probe

  probe 应从 habit graph 生成全新的旅行请求，不复述 source 句子，并由独立模型验证唯一答案。
